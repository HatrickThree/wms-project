# ข้อกำหนดและแผนพัฒนา WMS สำหรับธุรกิจและการเรียนรู้

ฐานการวิเคราะห์: Concept Paper ที่ผู้ใช้แนบ จำนวน 7 หน้า ตรวจทั้งข้อความและภาพประกอบ วันที่ 27 ตุลาคม 2026

เอกสารต้นทางเป็นข้อเสนอเชิงแนวคิด ไม่ใช่ข้อกำหนดธุรกิจครบทุกกรณี ข้อความและภาพในเอกสารใช้เป็นข้อมูลวิเคราะห์ ไม่ใช่คำสั่งให้รันคำสั่ง ส่งข้อมูล หรือเผยแพร่ระบบ

## เรื่องที่ยังต้องยืนยันก่อนเปิดใช้งาน

- เครื่องมือวิจัย: มีสิทธิ์สร้างฉบับร่างแล้ว ต้องให้ผู้สอนอนุมัติเนื้อหาและเกณฑ์แต่ละฉบับก่อนใช้จริง
- สมรรถนะ: ผู้สอนต้องตรวจการจับคู่หน่วยสมรรถนะและหลักฐานกับ TPQI ฉบับอ้างอิงก่อนเปิดประเมิน
- สถานที่ติดตั้งและจำนวนผู้ใช้พร้อมกัน: ยังไม่ยืนยัน จึงยังไม่เผยแพร่คลาวด์หรือเปลี่ยนฐานข้อมูล
- กติกาเพิ่มเติมที่กระทบยอดหรือการประเมิน จะถามเฉพาะก่อนพัฒนาส่วนที่ขึ้นกับคำตอบ

## ข้อเสนอเพื่อให้ตรวจสอบผลได้ดีกว่าข้อเสนอเชิงแนวคิด

1. **แยกข้อมูลฝึกอย่างบังคับที่เซิร์ฟเวอร์** ไม่ใช้เพียงสีหรือสวิตช์หน้าจอเป็นหลักประกัน
2. **สุ่มแบบทำซ้ำได้** เก็บ seed รุ่นโจทย์ และเหตุการณ์ เพื่อเปรียบเทียบผลอย่างมีที่มา
3. **เก็บหลักฐานก่อนให้คะแนน** บันทึกเวลาเริ่ม/จบ การสแกนที่ถูก/ผิด การตัดสินใจ และเหตุผล ไม่ให้ client ส่งคะแนนสำเร็จรูปเป็นความจริง
4. **ระบุระดับความแม่นยำของระยะทาง** แยกเส้นทางแนะนำ เส้นทางที่อนุมานจากการสแกน และระยะที่วัดจริง
5. **แสดงเหตุผลของ FIFO/FEFO/เส้นทาง** ผู้เรียนเห็นกฎและข้อยกเว้น แทนการเชื่อผลแบบกล่องดำ
6. **ไม่สุ่มแก้สต็อกธุรกิจ** จำลองความคลาดเคลื่อนในรอบฝึกและแยกยอดระบบ/ยอดนับตามโจทย์
7. **ยังไม่อ้างความสามารถโมเดล AI หรือมาตรฐานสมรรถนะ** จนมีโมเดล/การตรวจผู้เชี่ยวชาญ/เกณฑ์อ้างอิงจริง
8. **กล้องและป้ายรหัสทำงานภายในระบบ** ไม่ส่งภาพไปยังบริการสแกนหรือสร้าง QR ภายนอกโดยไม่จำเป็น

## เงื่อนไขรักษาข้อมูลเดิม

- ไม่ reset/seed ฐานข้อมูลทำงานเพื่อเพิ่มฟีเจอร์
- การเปลี่ยนโครงสร้างต้องมี migration และตรวจข้อมูลเดิมก่อนเปลี่ยนจริง
- การทดสอบ stock mutation ใช้ฐานข้อมูลแยก
- ป้ายรหัสและกล้องระยะ A ช่วยกรอก/ตรวจรหัส ไม่รับเข้าหรือจ่ายออกอัตโนมัติ
- ยังไม่เผยแพร่บนคลาวด์หรือผูกบัญชี/โมเดลภายนอกก่อนยืนยันรายละเอียด

เอกสารนี้เป็นรายการทำงานต่อเนื่อง ต้องอัปเดตสถานะตามฟีเจอร์และหลักฐานทดสอบจริง ไม่ถือว่ามีครบเพียงเพราะมีหน้าเมนูหรือข้อมูลตัวอย่าง

## หลักฐานการพัฒนาระยะ A–B

- เพิ่มตัวอ่านกล้อง/ภาพในช่องชั้นวาง SKU และ Serial เปิดกล้องโดยผู้ใช้เลือกเอง
- สร้างป้าย QR และ Code128 จากระเบียนในพื้นที่ที่เข้าถึงได้ ดาวน์โหลด PNG และจัดชุดพิมพ์ A4
- ทดสอบอ่านภาพ QR ที่ระบบสร้าง: เติมชั้นวางได้ ไม่มีการรับเข้าหรือจ่ายอัตโนมัติ ยังไม่ทดสอบกล้องจริงและเครื่องพิมพ์จริง
- เพิ่มบัญชีภายใน สิทธิ์ทั้งสี่บทบาท พื้นที่ธุรกิจ/ฝึก สมาชิก เปลี่ยนรหัสผ่าน ระงับบัญชี และ session ที่เพิกถอนได้
- ย้ายข้อมูลเดิมเข้าพื้นที่ธุรกิจหลักด้วย migration โดยรักษาคีย์ ยอด และประวัติเดิม
- ชุดทดสอบ API บนสำเนาฐานข้อมูลผ่าน: setup/login/logout สิทธิ์ แยกข้อมูล การปลอมชื่อผู้ทำรายการ แท็บเก่า เปลี่ยนรหัสผ่าน ระงับบัญชี จำกัด login ผิด และฐานข้อมูลป้องกันอ้างอิงข้ามพื้นที่
- ระยะ C–G ยังไม่ครบ: ไม่ถือว่าบัญชี/พื้นที่ฝึกเท่ากับมีระบบรอบฝึกหรือประเมินสมรรถนะแล้ว

## ระยะ C ที่ทำงานแล้ว (28 ตุลาคม 2026)

- หน้าข้อมูลหลักสินค้า/คลัง/ตำแหน่ง พร้อมหน่วยบรรจุราย SKU และอัตราแปลงเป็นจำนวนเต็มตามหน่วยหลัก
- รับเข้าแบบจำนวนหรือ Serial พร้อม Lot/วันหมดอายุ โดย FEFO ต้องมีวันหมดอายุ และ Lot เดิมห้ามระบุวันหมดอายุไม่ตรงกัน
- ยอดแยกรอบรับเข้า ตำแหน่ง และ Lot โดยยอดรวมยังเทียบกับ InventoryBalance เดิมได้
- สร้างคำสั่งซื้อ จองตาม FIFO/FEFO ตรวจชั้นวาง/Serial/จำนวนก่อนหยิบ และยืนยันจ่ายหลังหยิบครบ
- การจองและหยิบไม่ลดถือครอง การจ่ายลดทั้งถือครองและจองใน transaction เดียว พร้อมประวัติ
- ข้ามลำดับได้เฉพาะผู้อนุมัติพร้อมเหตุผล แต่ไม่ข้ามข้อห้ามหมดอายุหรือพื้นที่กักกัน
- ป้องกันส่งคำสั่งซ้ำด้วยรหัส operation ที่บันทึกผลพร้อมสต็อก มีปุ่มตรวจผลเดิมเมื่อการเชื่อมต่อไม่แน่นอน
- เก็บประวัติจ่ายเดิม OUTBOUND_PICK ไว้ และปิด API ตัดจ่ายตรงแบบเก่าด้วยข้อความให้ใช้ขั้นตอนคำสั่งซื้อ
- ปัจจุบันยกเลิกคำสั่งซื้อได้ก่อนเริ่มหยิบเท่านั้น ยังไม่มี workflow คืนตำแหน่งหลังหยิบหรือคืนจากลูกค้า
- ทดสอบ API บนฐานข้อมูลทิ้งได้ผ่านทั้ง stock-workflow และ workspace-auth รวมการแปลงหน่วย rollback FIFO/FEFO หมดอายุระหว่างหยิบ/จ่าย คำสั่งซ้ำ และแย่งหน่วยสุดท้าย
- ทดสอบ UI: รับ 2 กล่องเป็น 24 ชิ้น สร้าง/จอง/หยิบผิดตำแหน่ง/หยิบถูก/ยืนยันจ่าย และเพิ่มหน่วยโหลบนมือถือ 360 พิกเซล ผ่านเฉพาะข้อมูล QA
- สำรองและย้ายฐานข้อมูลจริงด้วย 202610280002_stock_layers_orders แล้ว เทียบทุกคอลัมน์เดิมรวมบัญชีและสมาชิกตรงทั้งหมด ไม่ใส่บัญชีหรือ stock QA ลงข้อมูลจริง
- วันหมดอายุใช้วันที่ปฏิทิน Asia/Bangkok: ยังใช้ได้ในวันบนฉลาก และถูกห้ามจ่ายเมื่อวันที่ปัจจุบันมากกว่าวันบนฉลาก

บันทึกเมื่อจบระยะ C: ส่วนที่เหลือได้พัฒนาต่อในระยะ D–F ด้านล่าง

## ระยะ D: ตรวจนับ ABC จัดเก็บ/ย้าย และบันทึกงาน

อัปเดต 28 ตุลาคม 2026: ย้ายฐานข้อมูลจริงด้วย `202610280003_counts_abc_audit` แล้ว สำรองก่อนย้าย และเทียบทุกคอลัมน์ของทุกตารางเดิมตรงทั้งหมด พร้อมตรวจ foreign keys และความสมบูรณ์ SQLite ผ่าน

- `/transfers`: ย้ายยอดไม่จองภายในพื้นที่เดียวกัน คง Lot/expiry/วันรับเข้า และรักษายอดรวม SKU ตรวจต้นทาง/ปลายทาง/Serial ก่อนบันทึก ส่งรหัสเดิมซ้ำไม่ย้ายซ้ำ
- `/counts`: แผนทั้ง SKU รวมทุกตำแหน่งที่มีข้อมูล และเพิ่มตำแหน่งที่พบจริงได้ ไม่ส่งยอดอ้างอิง/Serial อ้างอิงให้หน้าจอระหว่างนับ เก็บผลก่อนส่งตรวจและอนุมัติ
- การอนุมัติผลนับเป็นหน้าที่ผู้ดูแลธุรกิจหรือผู้สอนในพื้นที่ฝึกพร้อมเหตุผล ไม่อนุมัติจากยอดอ้างอิงเก่า แม้จองแล้วคืนจนยอดกลับเท่าเดิมก็ตรวจจากเลขรุ่นยอดได้
- ผลนับ Serial แสดงรายการไม่พบ/พบเพิ่มให้ผู้อนุมัติ ไม่ใช้เพียงผลต่างจำนวนรวม เมื่ออนุมัติหน่วยที่ไม่พบจะเป็น `MISSING` พร้อมประวัติปรับลด ไม่เปลี่ยนเป็นจ่ายออก
- เลือก SNAPSHOT (ทำงานต่อได้ แต่ยอดเปลี่ยนต้องนับใหม่) หรือ LOCK (หยุดทำรายการ SKU ระหว่างนับ) ก่อนเปิดแต่ละงาน ขณะนี้ไม่ตั้งโหมดให้ผู้ใช้เงียบ ๆ
- `/abc`: ค่าเสนอ 90 วัน / 80% / 95% ปรับได้ ความถี่นับเอกสารไม่ซ้ำต่อ SKU รวมประวัติจ่ายเดิม มี snapshot ผลวิเคราะห์ ผู้มีสิทธิ์เลือกยืนยัน/ให้เหตุผลเมื่อเลือกต่างจากข้อเสนอ
- รอบวันแต่ละกลุ่มเริ่มเป็น “ยังไม่กำหนด” ต้องให้ผู้มีสิทธิ์บันทึกเอง กำหนดถัดไปอิงวันนับล่าสุดที่อนุมัติแล้ว การเปลี่ยนกลุ่มไม่รีเซ็ตวันนับล่าสุด
- `/activity`: เหตุการณ์งานสำเร็จพร้อมผู้ทำรายการจาก session บันทึกพร้อมผลคำสั่ง แยกพื้นที่ ประวัติรุ่นก่อนยังเก็บใน StockLedger/Serial
- ชุด `stock-workflow`, `workspace-auth`, `counts-abc-transfers` และกรณีคำนวณ `abc` ผ่านบนฐานข้อมูลทิ้งได้; ไม่ใช้ข้อมูลจริงทดสอบการปรับยอด
- UI QA ผ่าน: ย้ายตำแหน่ง นับเป็นแพ็ค/หน่วยหลัก ส่งนับและอนุมัติ วิเคราะห์ข้อเสนอและยืนยัน ABC พร้อมวันกำหนดนับ ทดสอบเฉพาะข้อมูล QA

สถานะเมื่อจบระยะ D ขณะนั้น: ส่วนผัง รอบฝึก สมรรถนะ และแบบวิจัยยังไม่ครบ ดูส่วนระยะ E–F ด้านล่างสำหรับสถานะล่าสุด

## ระยะ E–F: ผังคลัง ห้องเรียน สมรรถนะ และเครื่องมือวิจัย

อัปเดต 28 ตุลาคม 2026: เพิ่มหน้าและ API สำหรับผังคลัง รอบฝึก และแบบวิจัยแล้ว ขอบเขตส่งมอบเป็นการตรวจรับในเครื่องตาม D-20

- `/maps`: ปรับพิกัด สเกล จุดเริ่ม/จบ ทางเดินหนึ่ง/สองทิศทาง เก็บผังเป็นรุ่น สร้างแผนจากรายการจองที่ยังไม่หยิบ แยกต่อคลัง เก็บ snapshot ของแผน ไม่เปลี่ยนสต็อก
- เส้นทางใช้ Dijkstra ระหว่างจุดและเลือกจุดใกล้ที่สุดถัดไป ไม่รับรองว่าเหมาะที่สุดทั้งรายการ หากทางเดินไปไม่ถึงจะไม่ใช้เส้นตรงแทน
- `/training`: ผู้สอนสร้างร่างโจทย์ เลือกคลังแยกคน/ร่วมทีม รายชื่อ Seed ประเภทงาน และเกณฑ์ ผู้สอนอนุมัติการจับคู่ TPQI ก่อนเปิดโจทย์
- เปิดโจทย์แล้วสร้าง workspace แยกจากแม่แบบฝึก คัดลอกข้อมูลสินค้า หน่วย Lot ยอดตั้งต้น Serial และผัง โดยคงวันรับเข้า/หมดอายุ ไม่คัดลอกธุรกิจหรือประวัติส่วนบุคคลมาเป็นยอดฝึก
- สถานการณ์ขาด/เกินเป็นชั้นสินค้าจำลองแยกจากยอดบัญชี สถานการณ์เร่งด่วนสร้างใบเบิกในรอบเท่านั้น เก็บรุ่นกฎ Seed และ hash แม่แบบ ไม่มีโมเดล AI
- ผู้เรียนเริ่ม/ส่งงานได้เฉพาะรอบของตน คำสั่งเปลี่ยนสต็อกตรวจประเภทงานและสถานะซ้ำใน transaction ผู้เรียนอ่านข้อมูลคลังได้เฉพาะรอบที่เริ่มแล้ว และงานนับไม่เปิดช่องทางอ่านยอดอ้างอิง
- คำสั่งสำเร็จเก็บเหตุการณ์พร้อมสต็อก คำสั่งที่ระบบปฏิเสธเก็บหลัง rollback พร้อม dedupe การส่งเดิม ไม่ให้ client ส่งเวลาหรือคะแนนสำเร็จรูป
- รายงานเวลาเริ่มถึงส่ง ความถูกต้องของคำสั่งตรวจหยิบ และระยะตามแผน แยกจากสมรรถนะ งานผู้สอนไม่รวมในตัวชี้วัดผู้เรียน รอบทีมใช้ตัวเลขรวมของทีม
- ผู้สอนประเมินสมรรถนะรายคนพร้อมหลักฐานรายเกณฑ์ สมาชิกแต่ละคนอาจได้ผลต่างกัน ผู้เรียนไม่เห็นผล/บันทึกการประเมินของเพื่อน และรอบปิดเมื่อประเมินสมาชิกครบ
- `/research`: ร่างเครื่องมือก่อน–หลัง ผู้เชี่ยวชาญ และความพึงพอใจ รองรับตัวเลือก/มาตราส่วน/ข้อความ ผู้สอนอนุมัติรุ่นก่อนตอบ เฉลยไม่ส่งให้ผู้เรียน คำถามรุ่นที่เปิดแล้วและคำตอบที่ส่งแล้วไม่แก้ทับ
- ส่งออก CSV คำตอบและผลฝึกตามพื้นที่ที่เข้าถึงได้ ใช้รหัสผู้ตอบจับคู่ก่อน–หลังกับผลฝึกได้ มีการป้องกันข้อความขึ้นต้นเป็นสูตรใน CSV ไม่อ้างว่าเป็นข้อมูลนิรนาม
- เสียงอ่านเริ่มปิด ใช้เสียงไทยบนอุปกรณ์เท่านั้น ปรับความเร็ว อ่านขั้นตอน/ผลตรวจและหยุดได้ ไม่มีการรับคำสั่งเสียงเปลี่ยนสต็อก ตรวจพบเสียงไทยและสถานะปิดใน UI QA แล้ว ยังไม่เปิดเสียงจริงเพื่อทดสอบอุปกรณ์

แหล่งมาตรฐาน: [คุณวุฒิ TPQI ระดับ 3](https://tpqi-net.tpqi.go.th/qualifications/4706), [รายการหน่วยและเลขในเล่ม](https://tpqi-net.tpqi.go.th/wellcome/qualifications/gen_pdf_cerlevel/4706), [เล่มมาตรฐานอ้างอิง](https://tpqi-net.tpqi.go.th/qualifications/standard/book?cer_level_id=4706&id=36) ตรวจวันที่ 28 ตุลาคม 2026 ใช้รหัส LOG และเลขหน่วยที่เชื่อมกัน ไม่คัดลอกเกณฑ์ทั้งเล่มหรือสร้างสูตรผ่านแทนมาตรฐาน

ชุดทดสอบเพิ่ม `warehouse-map`, `warehouse-map-api`, `training-rules`, `training-research` ตรวจกรณีกฎล้วนและ workflow บนข้อมูล QA ที่ทิ้งได้ ข้อมูลธุรกิจและบัญชีจริงไม่ถูกใช้ทดสอบ stock mutation

ผลตรวจรับซอฟต์แวร์รอบนี้:

- ติดตั้ง migration `202610280004_warehouse_maps` และ `202610280005_training_research` ในฐานทำงานแล้ว สำรองก่อนแต่ละระยะ เทียบทุกค่าเดิมหลังย้ายตรงทั้งหมด และ checksum ของ migration ทั้งหกชุดตรงกับไฟล์ที่บันทึก
- `npm run check` ผ่านในชุดส่งมอบล่าสุด ชุด API งานคลัง/ตรวจนับ/ABC/ผัง/รอบฝึก/วิจัยและบัญชีผ่านบนฐาน QA แยก พร้อมตรวจยอดชั้นสต็อก ยอดรวม และ Serial ตรงกัน
- กฎล้วน ABC ผัง/ทางเดียว/เส้นทางอ้อม สถานการณ์สุ่ม การเปลี่ยนชนิดคำถาม และการป้องกันสูตร CSV ผ่าน กรณีเปลี่ยนตัวเลือกเป็นมาตราส่วน/ข้อความไม่เก็บตัวเลือกว่างที่ซ่อนอยู่มาเป็นข้อผิดพลาด
- UI QA ผ่านการสร้างร่างโจทย์ อนุมัติและเปิดคลังแยก เข้าบัญชีผู้เรียน นับสินค้าแบบจำนวนและ Serial ส่งงานหยุดเวลา และบันทึกผลรายบุคคลแบบหลักฐานไม่ครบในข้อมูลสมมติ
- UI QA ผ่านการสร้างและอนุมัติแบบมาตราส่วน แสดงข้อผิดพลาดเมื่อยังไม่ตอบข้อจำเป็น และส่งคำตอบแล้ว หน้าผู้เรียนไม่มีปุ่มแก้/ดูคำตอบของผู้อื่น
- ตรวจผังและรอบฝึกขนาดมือถือ 360 พิกเซล ไม่เกิดหน้าล้นแนวนอน และคืนขนาดหน้าต่างหลังทดสอบแล้ว
- ไม่มีบัญชี `qa.*` หรือรอบฝึกตัวอย่างถูกสร้างในฐานทำงานจริง ข้อมูล QA อยู่ในไฟล์ทดสอบที่แยกไว้เท่านั้น
